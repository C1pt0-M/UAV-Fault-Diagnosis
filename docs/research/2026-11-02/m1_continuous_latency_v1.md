# M1连续回放时序与告警延迟v1

**固定18例源Val连续回放已完成并本地复算。M1没有每次固定额外200ms等待，但模型分数、确认与最终告警时间不同，多数最终事件依赖缺口或停止flush。不能据此宣称实时告警延迟只有约0.2秒。**

本文与[m1_training_and_response_results_v1.md](m1_training_and_response_results_v1.md)配套。仅使用此前固定的6正常＋12故障hover案例、seed42两采样组已选best；没有换跨度／阈值／规则、增加训练或查看最终test／Real。SIL/HIL案例配对且源Val已用于开发，结果只作描述。

## 1. 时钟、计算与真实发布点

原始ULog publication／observation时间、20ms发布网格和200ms因果残差保留。每个残差连续计算，滑动150帧窗口不重新等200ms；原150点相邻跨度2.98s，理想M0输入启动2.98s、M1需200ms历史＋2.98s。原消息不足、年龄、reset及严格全窗资格会进一步延迟。完整原生日志18例的M1相对M0输入就绪增量median0.20s、P90约3.038s、max3.36s，未把未标注的crop外日志拿来训练或算故障分数。

训练窗口stride5及cap64不代表部署预测节拍。此回放复用OnlineDetectionPolicy的每帧推理（20ms）、onset0.6／clear0.4、k_on/off3、min_event0.5s／merge0.5s。固定0.5用于分类越界，与事件onset0.6分别报告。连续3个高点的确认最少比候选晚40ms，但事件要闭合、通过最短时长再等合并，持续高分时最终通知可直到停止才发出。风险／preview与finalized fault通知分开，不拿lead_time_s充当真值延迟。

GTD首次激活与ULog command登记分别保留；这批GTD比command早32–128ms。它们均是注入记录参考，不是认证物理损伤起点。表内延迟以GTD为参照，command另在逐案例CSV列示。负／提前事件不记成参考后新检出，已跨越注入点的报警单独列出。

## 4. 推理、残差与20ms预算

RTX4090D，PyTorch2.5.1+cu124，单窗逐帧推理；不是无人机板载性能。保留第一个调用及所有长尾，无按结果删除。

原生流残差emit计算逐案例P90约0.737–0.890ms、最大2.670ms；归一化／设备传输median M0约0.121ms、M1约0.149–0.150ms。模拟每20ms处理残差工作，计入norm／transfer／forward并累积串行排队，M1就绪通常仍小于20ms；Uniform保留冷调用／系统长尾，M0最大225ms并造成11帧积压、M1最大29ms并造成1帧，不能保证最坏时延。

模拟没有计入原ULog解码、原生push／topic汇合成本、事件聚合和monitoring-session处理、网络／浏览器／真实接收调度。因此该就绪模拟是已计测量部分的预算诊断，不是全系统响应。最终事件的流时钟、模型壁钟与真实主机UTC各自保留，逐数组复算并未把不同主机时钟相减构造虚假真值。
