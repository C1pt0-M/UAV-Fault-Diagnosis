## 设置

- 全部 555 个源 val 案例，原裁剪时间轴，20 ms 网格。只要 150 帧历史窗全部输入合格，该帧就推理。
- M0 用 M0 B 的 best.pt；GBT 用内部 test 那次在全 train 上拟合的 pkl；ENS 是两者概率的平均。
- 事件策略用部署默认值：onset 0.6、clear 0.4、k_on 3、k_off 3、min_event 0.5 s、merge 0.5 s。两个模型用同一套，没有调。
- 一致性检查：在 cap64 位置重算出的窗口与 cache 逐元素相同（34710 窗，最大差 0）；M0 的 argmax 与保存的预测 0 处不一致。
- 内部 test 已加锁，本轮只用源 val，属于开发数据上的描述性结果，不设通过/失败门槛。

## 关键发现：窗口级改善没有转化为事件级改善

在独立正常上，ENS 每帧 ≥0.5 的比例比 M0 低（5.9% vs 8.2%），但最终误报事件反而多了约 2.4 倍。原因在于事件规则用的是 0.6 / 0.4 双阈值，而两个模型在正常窗上的分数分布形状不同（源 val cap64 窗）：

|悬停后段独立正常（280 窗）|≥0.5|≥0.6|<0.4|分数 10/50/90 分位|
|---|---:|---:|---:|---|
|M0|79.3%|8.2%|7.5%|0.41 / 0.53 / 0.59|
|GBT|50.0%|32.1%|40.0%|0.08 / 0.50 / 0.75|
|ENS|54.6%|19.3%|26.8%|0.24 / 0.52 / 0.64|

- M0 在悬停后段的分数大多卡在 0.5–0.6 之间：越过 0.5 算窗口误报，但很少到 0.6，所以在事件规则下大多不触发事件。
- GBT 和 ENS 的分数分得更开：越过 0.5 的少了，但越过 0.6 的反而多（ENS 19.3% vs M0 8.2%），于是确认出更多事件。
- 其他工况的独立正常也一样：≥0.6 的比例，M0 0.7%、ENS 1.9%。
- 逐帧看，ENS 在 0.6 上下穿越的次数比 M0 多（550 vs 414），分数抖动更大。

所以，此前以 0.5 为阈值的窗口级结论（含内部 test）**不能直接外推到部署事件规则**。窗口指标衡量的是 0.5 处的分类，事件规则衡量的是 0.6 处的持续性，两个模型的分数校准不同。

## 结论与边界

1. 在部署事件规则下，ENS 在源 val 上误报事件比 M0 更多，故障检出基本持平，确认延迟的 P90 更短。
2. 这不推翻窗口级结论，但说明 ENS 当前不能直接替换 M0 部署。要部署，需要单独处理事件阈值或分数校准，例如按模型自身的正常分数分布设定 onset。这需要在 train 内或新数据上冻结方案，不能在源 val 上调。
3. 独立正常只有 72 个案例、0.9 h，悬停 12 个案例；事件计数小，不做显著性推断。
4. M0 的低事件误报部分来自分数恰好卡在 0.5–0.6 之间，不代表 M0 在悬停后段真的分得清。
