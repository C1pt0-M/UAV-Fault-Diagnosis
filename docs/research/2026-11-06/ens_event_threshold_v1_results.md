# ENS 事件阈值：train held-out 选定，源 val 确认

日期：2026-11-06。协议：`configs/experiments/ens_event_threshold_v1.json`（运行前冻结）。脚本：`scripts/research/score_ens_frames.py`、`scripts/research/ens_event_threshold.py`。产物：`artifacts/ens_event_threshold_v1_20261106/`。

## 背景

[事件级回放](ens_event_replay_val_v1_results.md)发现：在部署事件规则下（onset 0.6），ENS 的误报事件比 M0 多。原因是两者分数分布不同。本轮只调 ENS 的 onset，其他事件参数不变；阈值在 train held-out 上选定，源 val 只用于确认。

## 设置

- train 的 2580 个案例，每帧由没见过该案例的折模型打分：M0 用 feature_groupcv_v1 的 3 个折 best.pt；GBT 按冻结配方逐折重拟合，在 cap64 窗上与保存的 held-out 概率逐元素相同（三折最大差都是 0）。
- val 的 555 个案例：M0 B best.pt，以及全 train 拟合的 GBT（与事件回放相同）。
- 每帧推理的条件：150 帧历史窗全部输入合格。
- 事件规则：clear 0.4、k 3、min/merge 0.5 s 固定。M0 用 onset 0.60；ENS 在 0.60–0.95 的网格上选。
- 选定规则：在 train held-out 的独立正常上，取每小时误报事件数 ≤ M0@0.60 的最小 onset。

## 补充（不属于冻结规则）：同一网格下 M0 也调阈值

为了排除"只是因为提高了阈值"，另外让 M0 也在同一网格上跑：

- 源 val 上，M0 从 onset 0.70 起独立正常误报事件就是 0，新确认 345–357；ENS@0.75 是 3 个误报、364 个新确认。
- train held-out 上，误报事件相近时 ENS 检出更多：M0@0.75 是 57 / 1567，ENS@0.80 是 58 / 1685；M0@0.90 是 24 / 1669，ENS@0.90 是 20 / 1715。
- 新确认数随阈值升高而增加，是因为高阈值减少了"参考点前已在报警"的跨越事件，更多案例在参考点后才确认。所以"新确认"不能单独当召回看，要和跨越数一起读。

**解读**：主要收益来自提高 onset 阈值本身，M0 同样适用。在 train held-out 上，同等误报水平下，ENS 仍比 M0 多检出约 50–120 个故障案例（约 2–5%）。在源 val 上，M0 调高阈值后误报已经降到 0，ENS 没有体现出误报上的优势。

## 结论与边界

1. 按冻结规则，ENS@0.75 通过，可以作为 Real 评估的候选。
2. 公平的对照不是 M0@0.60，而是同样调过阈值的 M0。部署默认的 0.60 对这两个模型都偏低。Real 评估应同时报 M0@0.60、M0 调阈值和 ENS@0.75，以免把调阈值的收益归给 ENS。
3. M0 的调阈值是事后补充，没有按同一规则选定。如果要正式比较，需要在 train held-out 上用同一规则给 M0 选阈值：按 M0 自己的误报目标取，ENS 那条规则的目标就是 M0@0.60，套到 M0 身上是循环的。最好事先约定一个共同的误报目标，例如每小时 ≤ X 次，再给两者分别选阈值。
4. val 独立正常只有 72 个案例、0.9 h，事件数很小。
