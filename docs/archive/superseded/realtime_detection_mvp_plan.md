# 实时故障检测 MVP 技术路线图

## 背景

当前项目已经具备以下基础：

- 已有基于 RflyMAD / RflySim 数据训练的在线二分类模型。
- 已有 PX4 实时遥测采集与统一 schema 适配机制。
- 已有实时检测服务、滑动窗口推理和故障事件聚合逻辑。

当前阶段的目标不是一步到位做高精度、强泛化、可定位的实时故障诊断系统，而是尽快形成一个可运行、可观察、可验证、可演示的 **实时检测 MVP（Minimum Viable Product）**。

## MVP 目标

MVP 阶段的核心目标是：

1. PX4 实时遥测能够稳定进入系统。
2. 系统能够构造有效滑动窗口并持续输出 `fault_prob`。
3. 能够基于连续检测结果聚合故障事件。
4. 能够通过日志、CSV 或 Dashboard 观察输入质量和告警结果。
5. 在不追求最终高精度的前提下，形成可复现的“实时检测闭环”。

## MVP 不追求的内容

当前阶段明确不追求：

- 实时四分类故障识别。
- 高精度故障定位与 fault isolation。
- 复杂多模型融合。
- 在线自适应训练或在线学习。
- 对所有 PX4 / Rfly 差异一次性完全解决。

## MVP 定义

本项目的实时检测 MVP 建议定义为：

> 在 PX4 仿真环境下，系统能够连续接收实时遥测，对固定大小滑动窗口执行在线二分类推理，并输出可解释的 fault probability 与事件级告警结果，同时能够保留数据质量信息以支持后续兼容性分析和模型迭代。

## 总体路线

建议按 4 个阶段推进，每个阶段都要求有明确可交付结果，不跳阶段推进。

---

## 阶段 0：实时输入链路打通

### 目标

确认 PX4 实时遥测能够稳定进入当前系统。

### 本阶段关注点

- MAVSDK / pymavlink / UDP 转发链路是否稳定。
- 时间戳、帧序号、采样频率是否正常。
- 实时帧是否能连续写入 CSV。
- 系统在几分钟量级飞行过程中是否出现明显掉线或停顿。

### 建议产出

- 至少 1 段 3~5 分钟的稳定 PX4 实时飞行 CSV。
- 1 份基础运行日志。
- 1 份链路状态记录，包括连接、掉帧、异常退出情况。

### 通过标准

- 实时链路可以稳定运行。
- 不出现大面积丢帧、卡死或持续断流。
- 原始数据可以完整落盘。

### 若未通过

若本阶段未通过，不进入模型验证阶段，优先排查：

- UDP 链路配置
- MAVSDK / pymavlink 字段采集
- 实时 receiver 稳定性
- 时间戳生成逻辑

---

## 阶段 1：Schema 适配 MVP

### 目标

确认 PX4 实时帧能够稳定映射成在线模型可接受的 canonical schema。

### 本阶段关注点

- 关键字段是否为 `mapped` 而不是大量 `default`。
- 派生字段是否稳定、数值是否合理。
- 输入通道是否能保持固定维度和固定顺序。
- 每个窗口中关键动态字段是否存在真实变化。

### 建议检查项

- `mapped / derived / default` 覆盖比例。
- 关键字段缺失率。
- 关键字段常数率。
- 关键字段是否存在明显异常值或恒定零值。

### 建议产出

- 1 份字段覆盖率报告。
- 1 份高风险字段清单。
- 1 份 canonical frame 示例记录。

### 通过标准

- 关键 IMU / velocity / baro 字段全部可用。
- 主体输入通道不是靠默认值拼凑。
- 在线窗口输入维度稳定，能持续构造 150 步窗口。

### 若未通过

若本阶段未通过，不建议直接试模型，应先回到兼容性方案文档，继续处理：

- 字段映射问题
- 派生字段稳定性问题
- 量纲和语义不一致问题

---

## 阶段 2：在线二分类检测 MVP

### 目标

先跑通 `normal / fault` 二分类的实时检测闭环。

### 原则

- 先有连续输出，再谈精度。
- 先确认事件逻辑稳定，再谈复杂诊断。
- 允许误报和漏报存在，但系统行为必须可观察、可复现。

### 本阶段输入

- PX4 实时帧
- 经过 schema adapter 的 canonical frame
- 固定滑动窗口（建议沿用 `150`）

### 本阶段输出

- 每个检测窗口的 `fault_prob`
- `label / confidence`
- 事件级结果：`start / end / duration / max_prob`

### 关注指标

- 系统是否持续输出 `fault_prob`
- 正常飞行下是否全程恒定高概率或恒定低概率
- 事件聚合是否稳定
- 正常段是否存在明显爆炸性误报

### 建议产出

- 一段实时检测结果日志
- 一段带时间戳的概率曲线
- 一份事件统计摘要

### 通过标准

- fault probability 连续可输出
- 聚合器能稳定形成事件，而不是每帧震荡
- 正常飞行段下系统行为可解释

### MVP 阶段建议目标

本阶段不要以“准确率”作为唯一标准，先以以下目标为主：

- 连续输出稳定
- 结果可观察
- 行为可解释
- 支持重复回放验证

---

## 阶段 3：规则辅助与告警优化

### 目标

在模型输出的基础上加入轻量规则层，提高系统稳定性和解释性。

### 这样做的原因

在 PX4 与 RflySim 尚未完全兼容时，单一神经网络模型容易受到 domain shift 影响。规则层不一定提升最终上限，但非常适合作为 MVP 阶段的稳定器和调试器。

### MVP 级规则建议

优先考虑 3 类简单规则：

1. **数据质量规则**
   - 关键字段长时间缺失
   - 某字段连续恒定不变
   - 突发异常尖峰

2. **物理一致性规则**
   - 电机输出与垂向加速度变化明显不一致
   - 姿态变化与角速度变化严重矛盾
   - 高度变化与速度变化关系异常

3. **传感器相关性规则**
   - 某些本应联动的通道关系被明显破坏

### 本阶段输出

- `model_fault_prob`
- `rule_flags`
- `final_alert_level`
- `alert_reason`

### 通过标准

- 告警结果比单纯模型更稳
- 可区分“模型异常”和“数据质量异常”
- Dashboard 或日志中可以解释告警原因

---

## 阶段 4：准实时回放验证

### 目标

把实时系统变成可重复、可复现实验对象。

### 这样做的原因

如果只依赖 live 测试，很多问题难以复现，无法区分是输入波动、时序调度问题还是模型行为问题。回放验证可以显著提高调试效率。

### 核心思路

- 录制 PX4 实时数据
- 固定输入数据回放
- 重复运行检测链路
- 比较同一条数据的多次运行结果

### 本阶段产出

- 1 组可重复回放数据
- 1 份回放结果摘要
- 1 套用于后续实验对比的基线输入

### 通过标准

- 同一份数据多次回放结果基本一致
- 能在离线条件下复现 live 中的问题
- 可以用回放数据稳定做 ablation 和调参

## MVP 推荐实现边界

### MVP 必做

- PX4 实时遥测接收
- 统一 schema 适配
- 滑动窗口在线二分类
- 事件聚合
- CSV / 日志 / Dashboard 可观察输出
- 基础规则辅助

### MVP 可选

- 正常飞行与异常飞行对照回放
- 数据质量评分
- 基础覆盖率监控面板

### MVP 暂缓

- 实时四分类
- 子系统级故障定位
- 模型蒸馏与模型压缩
- 在线训练与在线更新
- 多模态融合

## MVP 成功标准

建议将 MVP 成功标准拆成 4 类：

### 1. 工程成功

- 链路稳定运行
- 可连续处理实时帧
- 可产出事件级结果

### 2. 数据成功

- 输入覆盖率可接受
- 有效窗口占比高
- 关键字段不以默认值为主

### 3. 行为成功

- fault probability 输出稳定
- 正常飞行下不出现完全失控式误报
- 事件聚合逻辑合理

### 4. 调试成功

- 可以记录问题
- 可以复现问题
- 可以解释问题

## 失败判据

以下任一情况出现，说明当前 MVP 尚未成立：

- 实时链路无法稳定运行
- 无法持续构造有效窗口
- 模型输出长时间异常恒定
- 告警完全不可解释
- 同一输入下结果高度不稳定

## 推荐推进顺序

建议按以下顺序推进，不建议跳步：

1. 先做输入链路打通
2. 再做 schema 适配与覆盖率验证
3. 再做在线二分类 MVP
4. 再加规则辅助
5. 最后做准实时回放固化

## 当前阶段的决策建议

如果当前仍处于 PX4 与 RflySim 兼容性测试阶段，则本路线图建议：

- 暂时将目标锁定为“实时异常检测 MVP”，而不是“实时故障类型识别”。
- 先拿到可运行、可观察、可回放的闭环。
- 等兼容性结论清楚后，再决定是否进入兼容子特征集方案或 PX4 专用训练方案。

## 一句话结论

实时检测 MVP 阶段最重要的不是模型上限，而是先把 **实时链路、输入合同、滑动窗口、连续输出和事件聚合** 这条链路稳定下来。只要这个最小闭环成立，后续无论加规则、换模型还是做跨平台适配，都会顺很多。
